2.5 LightGBM and CatBoost

Alternative gradient boosting implementations

Author

Hua Gong

1 Learning objectives

By the end of this tutorial, you should be able to:

  • explain how LightGBM and CatBoost differ from a basic boosted-tree algorithm;
  • fit both models to NFL win probability data;
  • use early stopping without leaking test information;
  • tune the main complexity parameters;
  • distinguish their built-in feature-importance definitions; and
  • choose an implementation based on the data rather than brand recognition.

2 Three related implementations

XGBoost, LightGBM, and CatBoost all construct additive ensembles of trees. They differ in how they search for splits, grow trees, handle categories, and control overfitting.

Implementation Distinctive idea Especially useful when
XGBoost Regularized second-order boosting You want a mature, flexible general-purpose baseline
LightGBM Histogram splits and leaf-wise growth Data are large and training speed matters
CatBoost Ordered boosting and native categorical handling The data contain important categorical variables

These are tendencies, not guarantees. The best choice depends on validation performance, computation, interpretability, and maintenance requirements.

3 LightGBM intuition

Instead of evaluating every observed numeric value as a potential split, LightGBM groups values into histogram bins. This can substantially reduce the work needed to evaluate splits.

LightGBM also commonly grows a tree leaf-wise: it splits the current leaf with the largest estimated improvement. A leaf-wise tree can reduce loss quickly, but it can overfit small data if controls such as num_leaves, max_depth, and min_data_in_leaf are too permissive.

Suppose two candidate leaves would reduce the loss by 0.12 and 0.04. A leaf-wise procedure chooses the 0.12 leaf next. A level-wise procedure might split both leaves at the same depth, even though one offers much less improvement.

4 Fit LightGBM

analysis_matrix <- model_matrix(analysis_data)
validation_matrix <- model_matrix(validation_data)

lgb_analysis <- lgb.Dataset(
  data = analysis_matrix,
  label = analysis_data$home_win
)
lgb_validation <- lgb.Dataset.create.valid(
  dataset = lgb_analysis,
  data = validation_matrix,
  label = validation_data$home_win
)

lgb_parameters <- list(
  objective = "binary",
  metric = "binary_logloss",
  learning_rate = 0.05,
  num_leaves = 15,
  max_depth = 5,
  min_data_in_leaf = 50,
  feature_fraction = 0.80,
  bagging_fraction = 0.80,
  bagging_freq = 1,
  lambda_l2 = 1,
  seed = 431,
  verbosity = -1
)

lgb_fit <- lgb.train(
  params = lgb_parameters,
  data = lgb_analysis,
  nrounds = 500,
  valids = list(validation = lgb_validation),
  early_stopping_rounds = 30,
  verbose = -1
)

lgb_probability <- predict(lgb_fit, validation_matrix)
probability_metrics(
  validation_data$home_win,
  lgb_probability,
  "LightGBM"
)
# A tibble: 1 × 4
  model    brier log_loss accuracy
  <chr>    <dbl>    <dbl>    <dbl>
1 LightGBM 0.189    0.550    0.699

5 CatBoost intuition

Team, formation, venue, and play type are categorical variables. Converting a category to its overall outcome average can leak the target into its own feature. CatBoost combats this with ordered target statistics: for each training row, the encoded value is constructed using earlier rows in a random ordering rather than the row’s own outcome.

For example, suppose the earlier home-team outcomes in an ordering are (1,0,1). With a prior mean of 0.50 and prior weight 2, a smoothed category statistic is

1+0+1+2(0.50)3+2=0.60. \frac{1+0+1 + 2(0.50)}{3+2}=0.60.

The current row’s outcome is not used in its own encoding. CatBoost also uses ordered boosting to reduce another form of prediction shift created when the same observations define residuals and fit the next tree.

6 Fit CatBoost with native categories

This example adds play type to the common game-state predictors. CatBoost receives factor columns directly. Team identifiers were considered but rejected because they worsened game-grouped validation log loss; including a categorical variable is not automatically beneficial.

catboost_features <- c(
  wp_predictors,
  "play_type"
)

analysis_cat <- analysis_data %>%
  select(all_of(catboost_features)) %>%
  mutate(across(where(is.character), as.factor))

validation_cat <- validation_data %>%
  select(all_of(catboost_features)) %>%
  mutate(across(where(is.character), as.factor))

cat_analysis <- catboost.load_pool(
  data = analysis_cat,
  label = analysis_data$home_win
)
cat_validation <- catboost.load_pool(
  data = validation_cat,
  label = validation_data$home_win
)

cat_parameters <- list(
  loss_function = "Logloss",
  eval_metric = "Logloss",
  iterations = 400,
  depth = 4,
  learning_rate = 0.03,
  l2_leaf_reg = 10,
  random_seed = 431,
  od_type = "Iter",
  od_wait = 30,
  logging_level = "Silent"
)

cat_fit <- catboost.train(
  learn_pool = cat_analysis,
  test_pool = cat_validation,
  params = cat_parameters
)

cat_probability <- catboost.predict(
  cat_fit,
  cat_validation,
  prediction_type = "Probability"
)

probability_metrics(
  validation_data$home_win,
  cat_probability,
  "CatBoost"
)
# A tibble: 1 × 4
  model    brier log_loss accuracy
  <chr>    <dbl>    <dbl>    <dbl>
1 CatBoost 0.187    0.546    0.712

7 A fair comparison

When comparing implementations, hold the following elements constant:

  • the game-level training and validation split;
  • the outcome definition;
  • the information available at prediction time;
  • the primary scoring rule; and
  • the tuning budget.

Different models may need different representations. CatBoost’s native categorical features are part of its value, so requiring every method to use an identical numeric matrix can be artificially restrictive. Report this difference clearly.

8 What should be tuned?

Model High-impact parameters Important interaction
LightGBM learning_rate, num_leaves, min_data_in_leaf, feature_fraction, bagging_fraction Large num_leaves usually requires a larger min_data_in_leaf
CatBoost learning_rate, depth, l2_leaf_reg, random_strength, bagging_temperature Smaller learning rates normally require more iterations

For both implementations, begin with a deliberately large iteration limit and let early stopping choose the effective number of trees. Then tune structural and sampling parameters with the same grouped game splits. Tuning iterations independently of learning_rate is inefficient because they jointly determine how far the ensemble can move.

LightGBM’s leaf-wise growth makes num_leaves especially important. A depth limit of dd permits at most 2d2^d leaves in a complete binary tree, but a leaf-wise tree need not be balanced. Consequently, num_leaves should generally be substantially smaller than 2𝚖𝚊𝚡_𝚍𝚎𝚙𝚝𝚑2^{\texttt{max\_depth}} when both controls are active.

CatBoost’s default symmetric trees apply the same split condition to all nodes at a given depth. A depth-dd symmetric tree has up to 2d2^d leaves, so increasing depth can increase the number of leaf values exponentially.

9 How their built-in importance scores differ

LightGBM commonly reports:

  • gain importance: the sum of training-objective reductions from splits using a feature; and
  • split importance: the number of retained splits using the feature.

Gain and split count need not rank features the same way. One feature may create a few large improvements, while another appears in many small refinements.

For non-ranking CatBoost models, the default PredictionValuesChange importance measures how much model predictions change, on average, across pairs of leaves whose paths differ because of a feature. Leaf observation weights are used when aggregating those changes. LossFunctionChange instead approximates how much a selected evaluation loss worsens when the feature is removed from the model’s calculations. It requires evaluation data and can be negative.

None of these definitions supplies an effect direction or a causal conclusion. Tutorial 2.7 compares them with validation-set permutation importance calculated using the same log-loss scale for every model.

10 Practice questions

  1. Why can histogram-based splitting make LightGBM faster?
  2. What is the main overfitting risk of aggressive leaf-wise growth?
  3. Why should a row’s outcome not be used to construct its own target-encoded feature?
  4. If the data contain only eight clean numeric game-state variables, which CatBoost advantage is less relevant?
  5. Why is it inappropriate to choose the number of boosting rounds using the 2023 test season?
TipShow answers
  1. The algorithm evaluates a smaller set of binned candidate cut points instead of every distinct numeric value.
  2. It can repeatedly grow a small, highly specific region and fit noise. Limits on leaves, depth, and minimum leaf size help.
  3. That would leak target information and make training performance look unrealistically strong.
  4. Its native treatment of categorical variables is less relevant, although its boosting and tree construction may still perform well.
  5. The test season is intended to estimate performance on unseen future data. Using it for model selection makes that estimate optimistic.

11 Key takeaways

  • XGBoost, LightGBM, and CatBoost build the same kind of additive ensemble and differ in how they search, grow, and encode.
  • Histogram binning and leaf-wise growth make LightGBM fast but make num_leaves the critical control.
  • Ordered target statistics let CatBoost encode categories without leaking a row’s own outcome into its own feature.
  • Hold the split, target, information set, metric, and tuning budget constant when comparing implementations.
  • Each library defines importance differently, so always report which definition and which data set produced a ranking.
