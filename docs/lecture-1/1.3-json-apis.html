1.3 Working with JSON and APIs

Author

Hua Gong

1 Learning objectives

After completing this tutorial, you should be able to:

  1. explain the difference between HTML scraping and an API request;
  2. map JSON values to R data structures;
  3. build an HTTP request with query parameters;
  4. inspect and flatten nested JSON without losing record relationships;
  5. check HTTP and data-level errors;
  6. write a reusable API function; and
  7. handle authentication, pagination, rate limits, and caching responsibly.

2 APIs and JSON

An application programming interface (API) defines how software can request data or services. A web API commonly accepts an HTTP request and returns JSON.

HTML and JSON serve different primary audiences:

Format Primary audience Structure Typical R tools
HTML People using a browser Elements, attributes, and text rvest, xml2
JSON Programs exchanging data Objects, arrays, names, and values jsonlite, httr2

When a documented API provides the required information, it is usually preferable to scraping a visual page. An API can still change, limit requests, require authentication, or prohibit redistribution.

3 JSON data types

JSON has a small set of types that map naturally, but not perfectly, to R.

JSON value Example Common R representation
Number 34 or 0.625 Integer or double
String "BUF" Character
Boolean true Logical
Null null NULL or NA, depending on context
Array [3, 7, 0] Vector, list, or data frame
Object {"team":"BUF","score":34} Named list or data-frame columns

JSON objects and arrays can be nested to any depth. Do not begin by assuming that the response is already one rectangular table.

5 Create a tidy game table

The games object contains one row per game. Nested fields use names such as home.team and venue.roof after flattening.

games <- scoreboard$games

game_summary <- games %>%
  transmute(
    game_id,
    status,
    home_team = home.team,
    away_team = away.team,
    home_score = home.score,
    away_score = away.score,
    home_margin = home.score - away.score,
    venue = venue.name,
    roof = venue.roof

5.1 Work with a nested array

Each game also contains an array named drives. After parsing, this becomes a list-column: each row stores a small data frame of drive events.

drive_events <- lapply(seq_len(nrow(games)), function(i) {
  as_tibble(games$drives[[i]]) %>%
    mutate(game_id = games$game_id[[i]], .before = 1)

6 Validate parsed data

Parsing without an error only confirms that the JSON syntax was valid. It does not confirm that the correct records or fields were returned.

stopifnot(
  scoreboard$league == "NFL",
  nrow(game_summary) == 3,
  !anyDuplicated(game_summary$game_id),
  all(game_summary$status == "final"),
  all(game_summary$home_score >= 0),
  all(game_summary$away_score >= 0)
)

Validation should reflect the research question. For play-by-play data, for example, you might check the game key, play order, team identifiers, score progression, clock range, and duplicate play IDs.

7 Anatomy of an HTTP request

An API request may contain:

  • a method, such as GET for retrieval;
  • a base URL and endpoint path;
  • query parameters after ?;
  • headers, such as authentication or a user agent; and
  • an optional request body, most often with POST, PUT, or PATCH.

The server responds with a status code, headers, and usually a body.

Status range Meaning Examples
200–299 Success 200 OK, 204 No Content
300–399 Redirection 301 Moved Permanently
400–499 Client-side problem 400 Bad Request, 401 Unauthorized, 404 Not Found, 429 Too Many Requests
500–599 Server-side problem 500 Internal Server Error, 503 Service Unavailable

8 Build an API request with httr2

httr2 keeps the URL, parameters, headers, retry behavior, and response handling visible. The following request targets the historical 2019 MLB regular-season standings. It is not evaluated while this website is rendered because it requires live internet access.

standings_request <- request(
  "https://statsapi.mlb.com/api/v1/standings"
) %>%
  req_url_query(
    leagueId = "103,104",
    season = 2019,
    date = "2019-09-29",
    standingsTypes = "regularSeason",
    hydrate = "division,team"
  ) %>%
  req_user_agent("SGMT431 teaching example") %>%
  req_retry(max_tries = 3)

standings_response <- standings_request %>%
  req_perform()

resp_status(standings_response)
resp_content_type(standings_response)

req_url_query() safely encodes query parameters. req_perform() reports HTTP errors instead of silently treating an error page as data.

9 Parse a live response

One transparent approach is to obtain the response body as text and then parse it with jsonlite.

standings_raw <- standings_response %>%
  resp_body_string() %>%
  fromJSON(flatten = TRUE)

names(standings_raw)
str(standings_raw$records, max.level = 1)

The MLB response contains one record per division. Each record contains a teamRecords data frame. Preserve the division name when combining them.

records <- standings_raw$records

standings_2019 <- lapply(seq_len(nrow(records)), function(i) {
  teams <- records$teamRecords[[i]]

  teams %>%
    transmute(
      division = records$division.name[[i]],
      team = team.name,
      wins,
      losses,
      winning_percentage = as.numeric(winningPercentage),
      runs_scored = runsScored,
      runs_allowed = runsAllowed,
      run_differential = runDifferential
    )
}) %>%
  bind_rows()

standings_2019 %>%
  arrange(division, desc(wins))

10 Turn the request into a function

A reusable function collects the request, parsing, checks, and transformation in one place.

get_mlb_standings <- function(season, date) {
  response <- request(
    "https://statsapi.mlb.com/api/v1/standings"
  ) %>%
    req_url_query(
      leagueId = "103,104",
      season = season,
      date = date,
      standingsTypes = "regularSeason",
      hydrate = "division,team"
    ) %>%
    req_user_agent("SGMT431 teaching example") %>%
    req_retry(max_tries = 3) %>%
    req_perform()

  body <- response %>%
    resp_body_string() %>%
    fromJSON(flatten = TRUE)

  records <- body$records

  if (is.null(records) || nrow(records) == 0) {
    stop("The API returned no standings records.")
  }

  result <- lapply(seq_len(nrow(records)), function(i) {
    records$teamRecords[[i]] %>%
      transmute(
        season = as.integer(season),
        division = records$division.name[[i]],
        team = team.name,
        wins,
        losses,
        winning_percentage = as.numeric(winningPercentage),
        runs_scored = runsScored,
        runs_allowed = runsAllowed,
        run_differential = runDifferential
      )
  }) %>%
    bind_rows()

  if (anyDuplicated(result$team)) {
    stop("The returned team identifiers are not unique.")
  }

  result
}

standings_2019 <- get_mlb_standings(
  season = 2019,
  date = "2019-09-29"
)

11 Authentication and secrets

Some APIs require a key or token. Never type a secret directly into a .qmd file or commit it to a repository. Store it in an environment variable and allow httr2 to create the header.

api_key <- Sys.getenv("SPORTS_API_KEY")

if (api_key == "") {
  stop("SPORTS_API_KEY is not configured.")
}

authenticated_request <- request("https://api.example.com/games") %>%
  req_headers(Authorization = paste("Bearer", api_key))

Do not print request objects or headers when they may contain a secret.

12 Pagination, rate limits, and caching

Large APIs divide results into pages. Read the documentation to determine whether pagination uses page numbers, offsets, cursors, or links supplied in the response. Stop based on the documented rule, not an arbitrary number of loops.

For reliable and respectful use:

  • request only the fields and date range needed;
  • obey rate limits and Retry-After headers;
  • use retry logic only for temporary failures;
  • save permitted raw responses with retrieval metadata;
  • avoid repeatedly downloading unchanged historical data; and
  • distinguish an empty valid result from an error response.

14 Key takeaways

  • Inspect JSON structure before attempting to flatten it.
  • Preserve parent identifiers when expanding nested records.
  • Separate network errors, parsing errors, and data-validation failures.
  • Build URLs with query tools rather than manually concatenating unescaped values.
  • Keep API secrets outside documents and repositories.
  • Cache permitted historical responses and respect access limits.
